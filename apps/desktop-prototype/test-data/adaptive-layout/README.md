# 적응 조판(9단계) 검증 자산

분량에 따라 본문 문단 간격을 자동 조정하는 기능의 교정·게이트 자산이다.

## 구성

| 파일 | 역할 |
|------|------|
| `calibrate.py` | 측정기 교정. kordoc reflow 쪽수·채움률을 한글 COM 실측 쪽수와 대조 |
| `calibration.json` | 교정 결과(영속 증거). `safeFillThreshold` 값의 근거 |
| `gate.py` | 경계 분량 fixture 4종 게이트 |
| `gate-log.json` | 게이트 실행 기록 |
| `models/` | fixture 모델 JSON (커밋 대상 — 분량 정의가 곧 fixture다) |
| `out/` | 생성된 HWPX·PDF. **저장소 루트 `.gitignore`의 `out/` 규칙에 걸려 커밋되지 않는다.** 모델과 스크립트로 언제든 재생성되고 파일당 500KB급이라 그대로 둔다 — 증거는 `calibration.json`·`gate-log.json`에 남는다 |

```bash
npm run calibrate:layout-measure   # 교정 (COM 필요)
npm run verify:adaptive-layout     # 게이트 (COM 필요, calibrate 선행)
```

## 왜 2-pass인가

기존 `estimate_wrapped_lines`는 문자폭 900 고정 근사라 채움률 경계를 판정할 정밀도가
없다. 그래서 **생성 → 측정 → 간격 재조정 → 재생성**을 실제로 돌린다. 측정기는 한글
COM이 아니라 kordoc reflow다 — COM은 실행마다 다르게 실패해서(memory:
`hwp-com-kordoc-known-limits`) 루프 안에서 쓸 수 없다. COM은 이 교정과 최종 게이트에만 쓴다.

## 측정기 교정 — 왜 채움률 임계가 필요한가

kordoc reflow의 쪽수를 그대로 믿으면 안 된다. 실측으로 두 가지가 드러났다.

1. **줄높이를 한글보다 4~6% 작게 잡는다.** kordoc이 "1쪽에 들어간다"고 해도 한글에서는
   넘치는 구간이 있다.
2. **표 넘침을 쪽으로 나누지 않는다.** 표가 쪽을 넘겨도 kordoc은 쪽수를 그대로 두고
   채움률만 1.0을 넘긴다(1.18, 1.67까지 확인). 한글은 정상적으로 쪽을 나눈다.

COM 대조 실측값:

| kordoc 채움률 | 0.767 | 0.822 | 0.862 | 0.876 | 0.895 | 0.907 | 0.929 | 0.931 | **0.962** | 0.986 | 0.996 | 1.029 | 1.179 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| 한글 쪽수 일치 | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | **✗** | ✗ | ✗ | ✗ | ✗ |

경계가 `0.931`(들어감) ↔ `0.962`(안 들어감) 사이로 깨끗하게 갈리므로 안전 임계를 그
간극 중앙인 **0.945** 로 두고, 이를 넘으면 그 쪽은 넘친 것으로 보아 쪽수를 +1 보정한다
(`layout-tokens.json`의 `adaptiveSpacing.safeFillThreshold`).

임계를 낮추면 멀쩡한 문서를 조이고, 높이면 조이기 "성공"이 한글에서 거짓이 된다.
**본문 12pt 함초롬바탕 기준이므로 본문 글꼴·크기를 바꾸면 재교정 대상이다.**

보정 후 교정 표본 18종이 전부 COM과 일치한다(`calibration.json`).

## 게이트 fixture 4종

3종(넘침/적정/부족)만으로는 게이트가 공허하다. "원래 그 쪽수였는데 통과"나 "간격만
조이면 뭐든 한 쪽"이라는 거짓 수렴을 잡지 못한다. 그래서 각 케이스는 보정이 실제로
일을 했는지를 양쪽에서 단정한다.

| id | 모델 | 단정 |
|----|------|------|
| `A-overflow-rescuable` | `sweep-p36` | 보정 없이 COM 3쪽 **이면서** 보정 후 COM 2쪽 (보정이 load-bearing) |
| `B-comfortable-noop` | `sweep-p34` | 보정 no-op, 2쪽 유지 (과보정 차단) |
| `C-underfilled-loosen` | `sweep-p55` | 완화 적용되되 **쪽수 불변** 3쪽 |
| `D-overflow-unrescuable` | `sweep-p40` | 바닥값(140%)에서도 못 줄임 → 강제하지 않고 3쪽 정직 보고 |

D가 가장 중요하다. 조이기 사다리는 바닥이 있고(가독성 하한 140%), 거기서도 목표에 못
가면 **목표 쪽수를 강제하지 않는다**. 이 케이스가 없으면 "간격만 조이면 뭐든 줄어든다"는
거짓 수렴을 게이트가 통과시킨다.

## 알려진 비용

미리보기·내보내기가 보정 루프를 태우므로 후보 HWPX를 여러 번 생성한다(조이기 최대 4회
추가, 완화 최대 2회 추가). 무보정 경로보다 느리다 — 사다리 길이로 상한이 잡혀 있다.
